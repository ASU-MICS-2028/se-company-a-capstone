# Agile practices catalogue

The 20 practices Ghimire and Charters surveyed, in plain words:

| Practice | Meaning |
|---|---|
| Stand-up | 15-minute daily progress and blockers meeting |
| Continuous integration | Merge and build everyone's changes often |
| Continuous development | Routinely integrate changes into the main repo |
| Backlog | Prioritised list of work to deliver |
| Pair programming | Two developers at one workstation |
| Burndown/burnup chart | Visual record of work left or done |
| Definition of Done | Agreed criteria an item must meet before it counts |
| Definition of Ready | Criteria an item must meet before work starts |
| Refactoring | Improve code structure without changing behaviour |
| Scrum board / Kanban board | Visual status of work |
| Retrospective | Reflect on what worked, what didn't, and why |
| Epic | Big body of work split into user stories |
| Sprint/timebox | Fixed period to finish a set amount of work |
| User story | Feature described from the user's view |
| Planning poker | Team estimation game |
| Persona | Text portrait of a user |
| Automated test / unit test | Tests run on push / tests of single units |
| Online tools | Tools to visualise, track and communicate |

The course deck adds what each enables: stand-ups strengthen communication; stories clarify needs; refinement improves prioritisation; planning aligns work to capacity; retros drive improvement; CI gives fast feedback; testing builds confidence; charts make progress and risk visible; boards show bottlenecks.

## Use it in the capstone

Adopt at least 10 practices and list them in the paper's Methodology, each with evidence in the repo (board screenshots, CI runs, retro notes). The rubric's "planning and tracking" row needs that evidence.
