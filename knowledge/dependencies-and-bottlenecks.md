# Dependencies and bottlenecks

A **dependency** is a task that cannot start until another task is done. A **bottleneck** is a person or task that holds everyone else up.

The lecturer treats a bottleneck as a **planning failure**. If everyone has finished and one person is still working, then the Scrum Master, the product owner and the tech lead all got something wrong. The estimate did not match that person's ability, or the work was not staggered.

How to plan around it:

- **Map dependencies when you estimate.** Know what must come first and what can run in parallel. Give priority to tasks that others depend on, and get them done quickly.
- **Stagger the work so people can work at the same time.** Run parallel streams where possible.
- **Keep a quiet buffer.** If a task might take three days for someone new to it, set a two-day target but leave a light, movable task after it. If they overrun, push the light task back without blame: "We lost two days; let's make sure the fine-tuning is thorough in this window."
- **Fix it in the retrospective.** In one of his projects a single UI/UX designer held up several front-end developers because the pages were image-heavy. The retrospective caught it, and the team added another designer for the next sprint.

## Use it in the capstone

Note task dependencies in the sprint backlog (for example "needs API endpoint"). With six people, make sure no single person owns all the design or all the deployment work.
