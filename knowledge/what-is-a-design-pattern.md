# What is a design pattern

A **design pattern** is a named, reusable template for solving a design problem that keeps coming up. It is a blueprint or strategy for structuring code, **not the code itself**. Your code takes the shape of the pattern. If a problem only happens once, you do not need a pattern for it.

**Tailor analogy.** Tailors used to keep paper templates of the latest styles. A customer picks one, or asks for the top of one and the bottom of another, and the tailor combines them. Software engineers met the same problems again and again, so the best solutions were standardised. When you meet the problem, you pick the pattern and adapt it.

Patterns are abstract, and each one has a specific use (object creation, concurrency, data access and so on). They sit at the **design or architecture level**. They are a step before software architecture: patterns turn architectural intent into concrete components, relationships and responsibilities. Architectural styles are more abstract than design patterns.

The classic catalogue is the Gang of Four's 23 patterns.

## Use it in the capstone

Name the patterns we use in the architecture and design documentation, and say why each one fits. The lecturer marks justification, not just names.
