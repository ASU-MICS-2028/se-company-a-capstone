# Requirements classification matrix

Prosit 1 required **at least 12 requirements**, each classified with the question that defines its class:

| Class | Question it answers |
|---|---|
| Functional | What must the system do? |
| Non-functional | How well must it work? |
| Accessibility | What enables equitable access? |
| Usability | What makes interaction easy and effective? |
| Security/Privacy | How should user information be protected? |
| User-specific | What particularly serves our target users? |

Matrix columns: **ID | User need | Requirement | Classification | Priority**. For example, R02: "user needs to know order status" → "System shall communicate order status clearly" → Functional/Usability → High. A requirement may carry two classes.

Priorities use **Must / Should / Could** (MoSCoW). Requirements must come from evidence the team gathered, not be copied from the brief. The starting FR1–FR9 list was there to investigate, not to accept.

## Use it in the capstone

Use this matrix format for documentation section B1. Make sure the non-functional rows cover the brief's list: performance, usability, privacy, security, availability and reliability.
