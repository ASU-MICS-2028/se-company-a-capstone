# Capstone proposal contents

**Milestone 1** is a project proposal of **2 to 4 pages** ("not too elaborate"). It needs approval before we build, like an undergraduate thesis proposal. A **half-page project idea** goes in first, so the lecturer can give quick feedback before the full proposal.

Sections:

1. **Project title**
2. **Problem statement and motivation**
3. **Stakeholder analysis and user personas**
4. **System description:** a short paragraph on what it does
5. **Target users and use cases**, with UX considerations. Pick the significant use cases, not all of them. Follow one invented persona through a key journey end to end (for example, until they receive their order).
6. **Proposed architecture and programming model**
7. **Data requirements:** sources, tools, security
8. **Feasibility and scope for 6 weeks**
9. **Ethical, legal and social considerations**

Know the target users before writing use cases. AI can draft the structure, but tailor it with the team's own research.

## Use it in the capstone

Use this list as the proposal's table of contents. Each section later grows into a deliverable: personas and use cases into the UX doc, architecture into the C4 model, data and ethics into the paper.

## Also in Final project brief (SEE Fall 2026 Final Project Description), section 3

The brief lists **ten** headings. "Illustrative use case(s)" and "Target users and UX considerations" are separate items:

1. Project title 2. Problem statement and motivation 3. Stakeholder analysis and user personas 4. Proposed system description 5. Illustrative use case(s) 6. Target users and UX considerations 7. Proposed architecture and programming model 8. Data requirements (sources, flows, security) 9. Feasibility scope for 6 weeks 10. Ethical, legal and social considerations

Dates: concept note **13 Nov**, full proposal (Milestone 1) **14 Nov 2026**. "Approval is required before implementation begins." The idea must also pass the [project selection criteria](capstone-project-brief.md). Tips from the course rubrics: name indirect stakeholders too, build personas from evidence, and state the real need rather than "users need an app" (see [Grader expectations: explain, don't list](grader-expectations-explain-dont-list.md)).
