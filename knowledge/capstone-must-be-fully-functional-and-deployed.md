# Capstone must be fully functional and deployed

The lecturer repeated these expectations several times:

- **A fully functioning system**, not a loosely conceived prototype. Even an MVP (minimum viable product) can be loose. This must be a complete, working system.
- **Not on localhost.** It must be **deployed to free cloud hosting** and executable by others. A custom domain is welcome, and the lecturer may find a small budget for one.
- **The demo must not fail.** A failure in the live demo will be penalised, and he may re-run the demo to check whether a "glitch" was planned. "We ran out of time" counts as poor time management, not an excuse.
- **Stakeholder buy-in:** engage stakeholders so that real people are ready to use it.

Required components:

1. Software product (executable, deployed).
2. Complete software engineering documentation package, in the **GitHub repo** (industry standard), including a **Scrum-based project management** record and the technical **architecture and design** diagrams.
3. ACM-format research paper, 6 to 10 pages.
4. Presentation with a live demo.

To get there: assign tasks from day one and run rigorous **daily scrums**.

## Use it in the capstone

Set up the hosting and the CI/CD (continuous integration and delivery) pipeline in sprint 1, so we deploy continuously and the demo build is stable well before 18 December. Rehearse the demo on the deployed URL.
