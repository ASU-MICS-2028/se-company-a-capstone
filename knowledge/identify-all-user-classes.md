# Identify all user classes

**User requirements** start by classifying everyone who will use the system. The lecturer's advice: don't rush and don't stop at the obvious.

Who uses this classroom? Students and faculty, yes. Then technicians and cleaners. Then the electrician who fixes the air conditioner, firefighters during a fire, visiting officials, tourists on a campus tour. Each needs to engage with the space effectively.

Why it matters:
- Thinking through all possible scenarios is the difference between good software and software that is "just okay".
- You may not reach 100% coverage, but trying gets you close.
- In waterfall, this analysis must be exhaustive before building.

He encouraged teams to classify users and create **personas** (fictional but realistic profiles representing a user group) rather than doing the usual minimum.

## Use it in the capstone

Our UX doc should list every user class for our system (including admins, support staff, low-literacy or offline users) and give each key class a persona.
